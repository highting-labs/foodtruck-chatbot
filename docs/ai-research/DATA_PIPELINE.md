# 3. 회사 데이터 정제 및 적재 설계

- 작성: 2026-11-19 · 구현: `ai-research/rag/pipeline.py` (표준 라이브러리만) · 테스트: `ai-research/rag/test_rag.py`
- 원칙: 원본은 읽기만(쓰기 없음), 출력 폴더를 원본 폴더 안에 두면 실행 거부, 실제 고객 데이터는 외부 AI API로 보내지 않음

## 3.1 데이터 현황 (구조·건수만 조사, 내용은 읽지 않음)

| 순위 | 데이터 | 위치 | 규모·구조 | 지금 쓸 수 있나 |

- 익명본 메시지 중 금액이 나오는 메시지 5.8%, 인원·수량 7.9%, 날짜 3.4%, 메뉴 단어 8.6% → **대화 대부분은 인사·확인 말이고, 견적 정보는 일부 메시지에 몰려 있음**. 상담 단위 요약(구조화)이 검색 품질에 중요하다는 근거.

## 3.2 처리 단계

```
원본(읽기 전용)
 → ① 형식 분석      CSV(DATE,USER,MESSAGE) / xlsx는 zip 안 XML(셀·수식) / PDF는 텍스트 추출
 → ② 텍스트 추출    빈 메시지·사진/파일 표시 줄 제외
 → ③ 익명화         전화·이메일·계좌·사업자번호·도로명 번지·고객 이름(대화방 표시 이름에서 수집) 치환
                    대표번호 1877-6901, 회사·기관명, 지역, 금액, 메뉴는 남김(검색에 필요)
 → ④ 상담 단위 분리  한 대화방 안에서 3일 넘게 끊기면 새 상담
 → ⑤ 정보 추출       규칙 기반(기본) + LLM JSON 추출(선택, 로컬 모델만)
 → ⑥ 검증           확정 금액 근거, 지역·인원 누락, 개인정보 잔존 검사 → issues 칸
 → ⑦ 저장           cases.jsonl(상담 단위) · chunks.jsonl(6메시지 창, 2개 겹침) · report.json → pgvector
```

## 3.3 구조화 항목과 추출 방법

| 항목 | 칸 | 방법(PoC) | 한계 |
|---|---|---|---|
| 행사 날짜 | `event_date` | "N월 N일" + 대화 날짜 기준 연도(지난 달이면 다음 해) | "다음 주 금요일" 같은 상대 표현 못 읽음 → LLM 추출 |
| 행사 장소 | `region` | 지역 사전, 고객 말에서 **가장 먼저 나온** 지역 | "연수원" 속 "수원" 오탐 발견·수정(테스트 추가) |
| 행사 유형 | `event_type` | 키워드(창립·체육대회·축제·송년…) | 사전 밖 유형 누락 |
| 푸드트럭 종류 | `truck_types` | 메뉴 키워드 → 분류 | - |
| 예상 인원 | `people` | "N명/인분/잔/개" 최댓값 | 메뉴별 수량과 인원 혼동 가능 |
| 음식 종류 | `menus` | 메뉴판 이름(괄호 앞 이름 포함) 매칭 | 별칭(떡튀순 등)은 `lib/menu-source.js` ALIAS 재사용 필요 |
| 요청 사항 | `requests` | 전기·현수막·허가·실내·할인·여러 날·견적서 | - |
| 견적 금액 | `quote_total`, `quote_amounts` | 직원 말의 "총/합계/= N원" 중 **마지막** | 여러 안을 한 번에 주면 마지막 안만 |
| 추가 비용 | `extra_costs` | 출장비·발전기·현수막·실내부스·X배너 | - |
| 최종 협의 | `price_status`, `outcome` | 아래 규칙 | - |
| 고객 문의 / 직원 답변 | `customer_text` / `staff_text` | 역할별로 합침(익명화 후) | - |

### 가격 상태 규칙 (확정 견적 오인 방지)
- `confirmed`: 직원 말에 합계가 있고 + 확정 근거(직원 "확정·접수했·입금 확인" 또는 고객 "진행할게요·확정합니다·입금했")가 있고 + **마지막 합계 문장에 "대략·예상·정도·협의·다시 드릴게요"가 없을 때만**
- `negotiating`: 금액은 있으나 협의·조정·대략 표현이 있음
- `quoted`: 금액 안내만 있고 확정 근거 없음
- `no_price`: 금액 없음
- 검색·답변에서 **`confirmed`가 아닌 금액은 "확정 아님"으로 표시**, pgvector `confirmed_quote` 뷰에는 확정만 들어감.

## 3.4 PoC 실행 결과 (가짜 상담 12건, `ai-research/rag/sample_data/kakao/`)

- 실제 상담 원문 대신 같은 CSV 형식의 가짜 상담 12건을 만들어 시험(`make_samples.py`). 일부러 가짜 전화·이메일·계좌·주소·이름을 넣어 익명화를 검사.
- 결과: 12파일 → 12상담 → 12청크, 가격 상태 confirmed 5 · quoted 2 · negotiating 4 · no_price 1
- 사람이 정한 정답과 비교: 12건 모두 가격 상태 일치. 지역 11/12(1건은 원문에 지역 없음 → "지역 없음" 표시가 맞음)
- 익명화: 출력 전체에서 원래 전화·이메일·계좌·이름 0건(테스트로 자동 확인), 대표번호·금액은 유지

## 3.5 견적서 Excel 처리 설계 (미실행)

- xlsx는 zip 안의 XML이라 표준 라이브러리로 셀 값·수식을 읽을 수 있음. xlsb 1개는 바이너리 → `pyxlsb` 같은 패키지 필요(추가 전 승인).
- 회사 양식 2종(14칸, chatbot-developer 확인)이라 **셀 위치 매핑 표**를 한 번 만들면 규칙 기반 추출이 정확함: 상호·담당자·행사일·장소·품목(이름·수량·단가·금액)·출장비·합계·부가세.
- 견적서는 "보낸 견적"일 뿐 확정 여부를 모름 → 같은 고객·날짜의 상담·보드 행사와 맞춰 확정 여부를 붙임. 못 맞추면 `quoted`.
- 고객 상호·담당자·연락처는 익명화, 품목·금액·지역·날짜는 유지.

## 3.6 남은 결정·위험

- 익명본 1,290대화를 **로컬 파이프라인(외부 전송 없음)**에 넣어도 되는지 사용자 승인 필요(테스터 세션은 반출 금지 원칙, 개발 세션은 익명본 사용 권장 → 정책 확인).
- 규칙 기반 이름 익명화는 문장 속 별명을 놓칠 수 있음 → 적재 전 무작위 50건 사람 확인 + LLM(로컬) 2차 점검.
- 결과물(cases·chunks)도 회사 데이터이므로 저장소 밖(`workspace\_rnd_data\` 같은 곳)에 두고 커밋하지 않음.
